# ADR-033 — Builder-assisted generic Record updates

Status: Phase 12B is implemented on the feature branch and remains draft,
disabled, unqualified and unmerged.

## Decision

Phase 12A is complete as the frozen generic Record-creation subject. Phase 12B
adds the next operational proof: an authenticated Owner/Admin may update one
existing active Record belonging to one eligible existing Object. Product is an
acceptance fixture, not a Product-specific capability; Equipment and Catering
Enquiry use the same path.

The supported operation is `update_record`: one exact selector over one
supported scalar Field and one to three explicit absolute Field values. The
selector types are short text, email, phone, URL, number, currency, boolean,
date, datetime, select and status. Long text, multi-select and file selectors
are excluded. Relative arithmetic, fuzzy/substring matching, bulk/filter
mutation, null/File clearing, lifecycle changes, Relationships, Locations,
configuration changes and operational undo remain unsupported.

The model receives the unchanged AI-safe Business configuration context and a
validated one-step plan. It receives no operational Records, current values,
UUIDs or mutation authority and never chooses a Record ID. PostgreSQL is the
sole target/match authority: preparation returns only bounded not-found,
ambiguous, ineligible or ready state, with actual current values for the
confirmation. Candidate rows and full Records are never disclosed.

The signed 15-minute token binds the authenticated Business and actor and
contains only the action/schema envelope, base/head identity, target Object
identity, server-selected Record ID, expected `updated_at`, typed patch,
destination and token timestamps. The final action is AI-free and performs no
accounting or configuration mutation.

The final PostgreSQL boundary reads the Business head `FOR SHARE`, locks the
target Record `FOR UPDATE` once, verifies its active status and `updated_at`,
and applies the patch through the existing graph validation and timestamp
triggers. It does not re-query the selector, take an explicit Object
`FOR UPDATE` lock or duplicate the target lock. Replays and stale currentness
fail closed; a Record created after preparation does not invalidate the
server-selected original target.

Update eligibility derives Customer, Order and Order Item exclusions from
active trusted preorder capability mappings; Product remains eligible. No new
primitive, domain table, index, queue, history or receipt table is introduced;
the update is ordinary operational data and creates no configuration Change,
Version, history entry or rollback target. Product rename and Equipment
price/availability are the acceptance fixtures and use the same generic path.

## Consequences

The Builder confirmation UI shows the actual current values and bounded
before/after changes for one existing Record, states that the update will not
appear in configuration history, and lets the server choose the existing
internal View after success. The task remains global/default/private disabled;
no live compatibility, qualification or reliability evidence is claimed.

The frozen Phase 12A task, schemas, validator, scenarios, evaluator, policy
and evidence remain unchanged. Phase 12C and operational undo are deliberately
deferred.
