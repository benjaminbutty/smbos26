# ADR-033 — Builder-assisted generic Record updates use exact owner-supplied selectors, server-owned target resolution and explicit confirmation

Status: Phase 12B is implemented on the feature branch and is not merged.

## Decision

Phase 12A is complete as the frozen generic Record-creation subject. Phase 12B
adds the next operational proof: an authenticated Owner/Admin may update one
existing active Record belonging to one eligible existing Object. Product is an
acceptance fixture, not a Product-specific capability; Equipment and Catering
Enquiry use the same path.

The supported operation is `update_record`: one-to-three exact AND-only
selector clauses and one-to-five explicit absolute Field values. Selector and
update values must be grounded in the owner request. Relative arithmetic,
bulk/filter mutation, fuzzy or substring matching, null/File clearing,
Record-status changes, Relationships, Locations, configuration changes and
operational undo remain unsupported.

The model receives the unchanged AI-safe Business configuration context and a
validated one-step operational plan. It receives no operational Records,
current Record values, UUIDs or mutation authority and never chooses a Record
ID. The server canonicalises the selector, resolves at most two exact active
matches and returns only not-found, ambiguous, ineligible or bounded ready
state. Candidate Records are never disclosed.

Preparation returns an exact before-and-after confirmation. The signed
15-minute `update_record` token binds the Business and actor through the
existing operational envelope and contains only the signed target, schema,
selector, digest, patch and server-selected destination. The final action is
AI-free and invokes one confirmed generic update service call.

The final PostgreSQL boundary checks the configuration head, Object schema,
canonical selector digest, target Record digest and active status. Its lock
order is Business configuration head `FOR SHARE`, bounded selector read,
target Record `FOR UPDATE`, Object `FOR UPDATE`, selector rerun, digest checks,
then the existing `update_graph_record` RPC. The Record is locked before the
Object; Object-first locking is not used. The existing graph validation trigger
remains authoritative for the complete merged Record. Replays, target changes,
selector changes, ambiguity and configuration changes fail closed.

Update eligibility derives Customer, Order and Order Item exclusions from
active trusted preorder capability mappings. Product remains eligible. No new
primitive, domain table, index, queue, history or receipt table is introduced;
the update is ordinary operational data and creates no configuration Change,
Version or rollback target.

## Consequences

The owner-visible Product acceptance is `Celebration Box` → `Celebration
Platter`; the same Record ID and unmentioned values remain unchanged. The
Equipment acceptance changes Projector hire price to £65 and availability to
false atomically. Both use the same task, validator, selector resolver,
composer, token, RPC, trigger, UI and server-selected internal View rule.

Phase 12B has an independent disabled/Terra task policy and compatibility,
qualification and reliability harness. The frozen Phase 12A task, schemas,
validator, scenarios, evaluator, policy and evidence remain unchanged. Phase
12C and operational undo are deliberately deferred.
