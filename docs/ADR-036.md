# ADR-036 — Direct Table Workspace is a bounded owner-facing configuration facade

Status: Accepted for v0.1 (Milestone 15 Phase 15A)

## Context

Before this phase, owner-facing configuration work went through a visible
propose, preview, validate and apply journey. Phase 14A inline-edit evidence
and the Phase 14B manual-list flow showed that this ceremony was
disproportionate for a deliberate, bounded internal Table action such as
adding a column or changing its label. The owner manipulating a Table is
already making the apply decision; safety remains server-owned shape,
currentness, validation and immutable history.

## Decision

SMBOS adds a direct Table Workspace for Owner/Admin users over the existing
Object, Field, View, Record and Milestone 5 configuration-version primitives.
The Tables sidebar is the primary creation and navigation surface. It lists
active internal Table Views exactly once; non-table Views and ordinary Pages
retain their existing navigation behavior. The retired generic Lists route is
kept only as a compatibility redirect.

The direct structural action vocabulary is finite: create a Table, rename its
title, add a column, rename a column, change Choice/Status options, reorder
columns, and resize a column. A newly created Table emits only one custom
Object, one required short-text `Name` Field and one internal Table View. It
does not create a Form, Page, Relationship, workflow, queue or concept-specific
database table. Labels, supported column types, options, keys, widths and
currentness are validated before composition.

The browser sends only a bounded intent and expected active Version/head. The
server reloads the immutable configuration snapshot and composes ordinary
`set_object`, `set_field` and `set_view` operations. PostgreSQL is the final
authority: the authenticated direct RPC checks the action shape against the
base and candidate snapshots, then calls the existing M5 propose, validate and
apply functions in one transaction. The direct action itself is the owner's
apply decision; it still produces an ordinary applied Change, deterministic
diff, immutable Version and head advance. Direct Undo derives only the immediate
parent of the active direct change, verifies its provenance and uses the
existing rollback preparation, validation and application path. Any failure
rolls back the whole direct request.

Direct Undo also checks operational data before rollback. Undoing a direct
`create_table` is unavailable once any Record exists for the created Object;
undoing a direct `add_column` is unavailable once any Record has a meaningful
value for that Field. Rename, reorder and resize remain subject to the normal
configuration compatibility checks. This prevents the ordinary M5 allowance
for archived later identities from becoming a silent loss of Table access.

Column widths are an optional `column_widths` map inside the existing Table View
configuration. Keys must be visible Field keys and values are integer pixels
from 128 through 640. This is a reusable View layout setting, not a new
primitive or persistence model.

The live direct Table route renders a generic grid with inline cell editing,
keyboard navigation, row creation from configured Forms or visible Fields and
defaults, and a query-parameter record panel. Direct edits re-resolve the
Business, Table, Object, Field and Record and write through the existing
GraphService operation boundary. A legacy Table with an `edit_form_key` uses
the existing edit Form's non-hidden Fields as its direct-write whitelist; a
formless Table uses only metadata-derived supported Field types. They are
operational Record writes and never advance configuration history. The Record
panel presents the Table name and Record status and links to the full Record
route for existing Location availability controls. Candidate preview remains
read-only, and the existing full Record route remains the fallback for
non-direct contexts.

AI, Builder planning, provider policy, accounting, arbitrary operations and
the ordinary Changes lifecycle are unchanged. The direct lane is a narrow
manual owner-facing adapter over M5, not a second truth model. The reviewed
Changes lifecycle remains required for AI, public, destructive and
incompatible work, and for historical rollback.

## Consequences

Non-technical operators can create a reusable generic concept and manage its
Table without learning Builder or database terminology. Structural actions
apply atomically and remain visible in History as ordinary configuration
Versions. Direct Undo is intentionally limited to the immediately active
direct action; historical configuration rollback remains in Changes. Broader
Field settings, deletion/archive, formulas, relations, permissions, bulk
editing and spreadsheet behavior remain deferred.

The old Phase 14A repeated `value [Edit]` control is superseded on the direct
Table route by cell interaction and the Record panel; its trusted one-Field
GraphService mutation boundary is retained. The Phase 14B Lists wizard and
proposal UI are superseded by the Tables sidebar, while its generic composer
and tests remain historical regression evidence. Existing Forms, Pages and
ordinary Changes routes remain functional for legacy and reviewed flows.
