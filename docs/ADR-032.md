# ADR-032 — Builder-assisted generic Record creation

Status: Phase 12A feature branch; not claimed as merged.

## Decision

Builder-assisted creation of one generic graph Record uses the existing graph
Object/Field model and the ordinary Record insert trigger. A ready one-step
`create_record` plan is converted into a strict, transient typed intent. The
server validates the target Object, eligible writable Fields and typed values,
reads authoritative defaults, and requires explicit Owner/Admin confirmation.

The confirmation token is a short-lived HMAC envelope bound to the
authenticated Business and actor. The final action rechecks the exact
Object/schema/state currentness, then calls one narrow
`create_confirmed_graph_record` RPC. PostgreSQL locks the Business head for
share, the Object definition for update, and inserts the Record atomically;
existing validation triggers remain authoritative. A stale or replayed token
fails closed without a second insert.

The model receives the unchanged AI-safe Business context and ready plan. It
may return only exact existing Object and Field keys present in the supplied
configuration context. It may not invent new keys, UUIDs, IDs, defaults,
Records, relationships or mutation authority. The default and production
mappings remain disabled; the Terra policy and live
qualification/reliability harness are engineering-only and separately gated.

Eligibility requires an existing active target Object with at least one active
non-file writable Field, no active required incoming Relationship that makes
standalone creation incomplete, no active preorder Order or Order Item Object
mapping, and no required File Field without a usable default.

`7c03b743480016f24c5d6922ec6e4933103dce35` stopped on
`product_text_currency_default`, repetition 1, with `passed: false`,
`output_state: null`, `field_value_count: 0`, `failure_class:
provider_execution`, `failed_gate_codes: [provider_execution]`, one attempt,
incomplete usage, zero input/output tokens, zero estimated microusd,
`elapsed_ms: 1061`, `error_code: ai_execution_failed` and
`validation_reason_code: null`. The qualification aggregate was 8 total
scenarios, 0 passed, 1 failed, 1 attempt, zero input/output tokens, zero
estimated microusd, 1061 ms and exit code 1. No model output was returned or
evaluated.

The existing redaction prevented exact invalid-request stage classification.
The cause is intentionally not guessed: local `OpenAiSchemaAdaptationError`
and provider HTTP 400/422 failures were both mapped to public
`StructuredAiProviderError(kind: invalid_request)`. The bounded correction
adds only the finite internal stages `local_schema_adaptation`,
`provider_schema_rejected`, `provider_response_format_rejected`,
`provider_model_rejected`, `provider_parameter_rejected` and
`provider_invalid_request_unknown`. A depth- and cycle-bounded exact-class
cause traversal carries the code only to the engineering evaluation report as
`provider_reason_code`; public AI errors and Business audit metadata remain
unchanged and raw provider material is never emitted.

Deterministic transport coverage proves that the exact registered Record
output schema succeeds through draft-7 JSON Schema generation, the OpenAI
adapter and an injected Responses client, which receives one valid request.
Reliability was not run, qualification was not rerun, production remains
disabled, and no additional live provider spend occurred.

The operator subsequently ran the same first qualification scenario against
exact head `a6054b63477664cc9e422e4c2cb6e8179dcddd84`. It again stopped before
model output, with `passed: false`, `output_state: null`,
`field_value_count: 0`, `failure_class: provider_execution`, one attempt,
`usage_complete: false`, zero input/output tokens, zero estimated microusd,
`elapsed_ms: 715`, `error_code: ai_execution_failed`,
`validation_reason_code: null` and `provider_reason_code:
provider_schema_rejected`. The aggregate was 8 total scenarios, 0 passed, 1
failed, 1 attempt, zero tokens, zero estimated microusd, 715 ms and exit code
1. No model output or scenario quality was produced or evaluated.

This is evidence-supported transport diagnosis: the Record URL variant had
been built with `z.string().url()`, whose draft-7 JSON Schema emitted
`format: "uri"`; the documented OpenAI Structured Outputs format subset does
not include `uri`. The correction replaces that URL transport shape with a
bounded structural string (`minLength: 1`, `maxLength: 2048`, HTTP(S) prefix
pattern) and keeps URL syntax and exact `http:`/`https:` protocol validation
in the shared deterministic runtime schema. The OpenAI adapter now explicitly
allows only `date-time`, `time`, `date`, `duration`, `email`, `hostname`,
`ipv4`, `ipv6` and `uuid`, and fails unsupported formats locally. Reliability
was not run, production remains disabled, and no further live spend occurred.

## Consequences

Product-specific creation is not added to the platform. Generic concepts such
as Equipment and Catering Enquiry use the same Object/Field/Record path, with
no new table, primitive, queue, receipt table or configuration version. The
existing runtime reads the newly created Record through the selected internal
View. Preparation and confirmation are deterministic after the intent task;
the final action performs no AI call, accounting reservation, configuration
mutation or provider call.

The state RPC and confirmed-create RPC are the new database boundary. They
return only the bounded state/result needed by the server, enforce tenant and
capability checks, and use PII-free schema/state digests for currentness. The
implementation is intentionally limited to one generic Record and does not
add Record update/delete, relationship creation, file upload, public form
changes, or generic operational action dispatch.
