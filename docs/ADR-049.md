# ADR-049 — Builder clarification uses a signed bounded continuation, not chat memory

**Status:** Accepted
**Date:** 25 August 2026

## Context

The former Builder clarification panel left the original textarea active and
asked the owner to reconstruct a larger request. That lost intent between
turns and encouraged loops.

## Decision

When planning needs clarification, Builder replaces the request composer with
answer controls for the returned question metadata and a compact preserved
request. A server-signed, actor-and-Business-bound continuation carries only:

- original owner request;
- active configuration version/currentness;
- current questions and prior answers;
- schema version, round and expiry.

The continuation uses the existing HMAC operational-envelope primitive with a
distinct action and signing namespace. It is valid for 15 minutes, allows at
most three question rounds, five questions per round, 1,000 characters per
answer, 5,000 total answer characters, an 8,000-character composed planning
request and the orchestration's 16 KiB UTF-8 input ceiling. The server verifies identity and configuration currentness before it
composes the original request with established answers and calls the existing
planner. A later clarification receives a newly signed continuation; a ready
result follows the existing proposal or operational-confirmation path.

## Consequences

- The owner answers the question directly; no request reconstruction, browser
  authority or permanent conversation state is introduced.
- Tampering, wrong actor/Business, expiry, configuration drift and exhausted
  rounds fail closed with no proposal or mutation authority.
- The existing AI accounting and proposal-only orchestration remain in place.
- Refresh continuity is deliberately not claimed: the continuation is short
  lived and the UI makes no persistence promise.

## Exclusions

There is no Builder chat transcript, provider-response storage, search,
long-term AI memory, automatic Apply, automatic Publish or model mutation
authority.
