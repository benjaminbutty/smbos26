# ADR-046 — Internal Pages use one bounded Tiptap candidate and explicit save

**Status:** Accepted for the Interaction Quality Reset
**Date:** 24 August 2026

## Context

ADR-037 established Tiptap as a client adapter over the strict SMBOS Page
grammar, but deliberately deferred rich text and described layout autosave.
Journey 3 later presented internal Pages through per-block React forms and one
configuration write for each completed block operation. Owner review rejected
that interaction: the live surface does not behave like a continuous document
and ordinary composition is interrupted by repeated block save states.

The existing primitives and trust boundaries are sufficient. The defect is in
the bounded Page grammar and internal authoring presentation, not in Page
identity, persistence, rendering, tenant isolation or configuration history.

## Decision

Internal Owner/Admin Pages use one Tiptap `EditorContent` document held in
component memory. Typing, formatting, insertion, movement and local undo/redo
mutate only that candidate. `Save page` or Cmd/Ctrl+S translates the complete
candidate into the canonical SMBOS Page grammar and invokes the existing
`save_page_layout` Direct Page action once. One successful body save therefore
creates exactly one applied Change and one immutable Version. A stale or failed
save retains the local candidate and fails closed. Navigation and refresh warn
while meaningful unsaved body work exists. No database draft, browser storage,
background save or Version-per-keystroke is introduced.

The canonical grammar gains a finite, platform-owned rich-text block. Its
top-level node is exactly one paragraph, heading level 1–3, flat bulleted list
or flat numbered list. Inline content is bounded text with only bold, italic
and validated safe-link marks. Existing Heading, Text, Divider, Callout, View
and capability/historical blocks remain valid and round-trip. Unknown nodes,
marks, attributes, HTML and editor JSON remain invalid. TypeScript and
PostgreSQL validate the same finite grammar.

The Page title remains the existing separate `rename_page` direct action. In
this reset, “one Page save” means one complete body candidate and one Version;
a deliberate title rename is a separate configuration action. This avoids a
new compound lifecycle while keeping the save consequence predictable.

Internal and Site authoring may use separate presentation components, but both
must retain the same Page primitive, canonical grammar, `PageRenderer`, Direct
Page service and configuration lifecycle. Existing draft-Site saves and
ADR-045 published-Site candidates are unchanged. Public Pages do not gain new
editing controls or publication behavior through this decision.

## Consequences

- ADR-037 is amended only where it described internal Page autosave and
  deferred the bounded rich-text grammar above.
- Raw Tiptap/ProseMirror JSON is still never authoritative or persisted.
- The Page body becomes a real continuous document without adding a second
  Page runtime or persistence model.
- Existing and historical Page blocks remain readable and render through the
  existing runtime.
- The additive migration changes Page shape validation only; it adds no table,
  column, RPC, role grant or tenant-owned storage.
- Sites/publication, media, widgets, arbitrary nested documents, collaboration,
  comments, templates, CSS/HTML and persistent drafts remain excluded.
