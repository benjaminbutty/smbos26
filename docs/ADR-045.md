# ADR-045 — Published Site edits use one memory-only candidate and atomic publication

**Status:** Amended for Lenni Sites C1; legacy J3-I4 rule retained until adoption
**Date:** 22 August 2026

## Context

The accepted public Page runtime resolves one authoritative active `public` and
`published` Page. The authenticated Site editor currently applies each Direct
Page title or layout action immediately, so experimentation on an already
published Site changes what customers see without a publication consequence.

Journey 3 requires deliberate publication without introducing a durable Site
draft, second Page, second renderer or second configuration lifecycle.

## Decision

An already-published Site holds its bounded candidate title/layout only in the
active client component. The candidate is previewed by the existing
`PageRenderer`; navigation and refresh warn when it differs from the latest
authoritative published Page. Discard restores that latest baseline.

One finite `publish_page_changes` Direct Page action submits the trusted Page
key, expected currentness, bounded title and strict complete layout. The server
derives tenant and actor, reloads the active immutable snapshot, requires an
active public published Page and composes one complete `set_page` operation
that preserves key, slug, audience, published status and active state.

Heading, Text and Divider content may change. Existing capability and
historical atoms remain exactly configured and may only be reordered. The
TypeScript composer and PostgreSQL action-shape guard both enforce this rule.
The existing atomic direct configuration boundary creates exactly one applied
Change and immutable Version. The anonymous resolver changes only after that
transaction succeeds.

Draft Sites continue saving private bounded Page actions and use the existing
separate initial **Publish Site** action.

## C1 amendment — durable multi-Page release foundation

Lenni Sites C1 adds a private coordination foundation for a future shared Site
reader. It does not activate that reader, change anonymous routes, or adopt an
existing public Page. The J3-I4 memory-only candidate remains the authority for
an existing published Page until an explicit C2 adoption is reviewed.

A Business may have one durable, revisioned Site composition with up to twenty
draft Pages. The composition is a strict V1 grammar built from canonical Page
atoms plus bounded section, gallery, collection and collection-detail atoms.
Internal Pages retain the ADR-052 grammar; Site atoms are accepted only in a
public **draft** backing Page and are rejected from public published Pages until
the C2 release reader exists. Forms and definition changes remain a future
finite C3 extension, not a permanent exclusion.

The owner-visible Site slug belongs to the Site composition and immutable
release projection. C1 derives a distinct, stable backing Page key and backing
slug from the trusted Site/Page identities, so a Site `/about` can coexist with
an internal Page `about` without changing either legacy key or URL. Callers do
not choose canonical Page IDs, keys, backing slugs, configuration operations or
public projections.

Saving is guarded by the Site draft revision and its exact configuration base.
A changed configuration head requires an explicit rebase rather than silently
moving a stale Site composition forward. Preparing locks selected Records in a
deterministic order and freezes their approved field values into an immutable,
size-bounded release projection. The candidate records the active-release
revision it observed. Publishing replays an already-published candidate as its
original success, but otherwise compares that revision before selecting it, so
a stale candidate cannot move a newer pointer backwards.

When a Site-derived canonical Page definition changes, the server derives the
finite `set_page` operation and applies it through the ordinary configuration
change/version lifecycle in the same transaction as release selection. When
the canonical definition is unchanged, publication creates its immutable Site
release audit and selects it without a synthetic configuration Change or
Version. Both paths assert that the immutable configuration snapshot still
matches the current configuration projection before they proceed.

Draft and release media references participate in cleanup claims. A claim is
exclusive and retained across an uncertain storage deletion result; a retry may
remove/finalize with the token it received, while another worker cannot attach
or race that asset. Existing Page image and gallery attachment checks also
reject claimed or foreign assets.

## Compatibility plan

- Existing public Pages, their J3 publication flow, public resolver and URLs
  remain untouched in C1.
- C1 refuses a Site transition that would bind or overwrite a legacy published
  Page, or any backing Page that is not already owned by the trusted Site
  binding.
- Configuration readers parse the extended public-draft layout shape while
  retaining the ordinary grammar for internal and published Pages. This keeps
  Direct Table and internal Page operations compatible with snapshots that
  contain a C1 backing Page.
- C2 must rehearse an explicit legacy adoption, install the release reader and
  switch authority deliberately. A missing or invalid release fails closed;
  C1 never exposes a mutable draft to anonymous readers.

## Consequences

- Public content remains unchanged during published-Site experimentation.
- Stale or failed publication leaves the previous public Page intact and keeps
  the in-memory candidate for owner review.
- Refresh or session loss discards the candidate after an explicit browser
  warning; no durable draft is implied.
- The legacy J3 path introduces no new primitive, table, draft store, renderer,
  public runtime or publication pointer. The C1 amendment introduces only the
  private coordination tables above and does not activate a reader.
- Button/Image editing, capability configuration/removal, arbitrary layout,
  branding, media, domains, SEO and partial publication remain excluded.
